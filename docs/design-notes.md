## 1. 目的と確定事項

runnora 用の runn シナリオ YAML を、テストレビュワーが内容を確認し、記録として保存できる手順書原稿へ変換する。実装言語は Go とする。

| 項目 | 確定した方針 |
|---|---|
| 入力範囲 | シナリオ YAML、参照先 YAML/JSON、設定や追加指定による前後処理 SQL/PLSQL |
| 通信方式 | HTTP、gRPC Unary RPC、gRPC Server streaming RPC |
| gRPC の対象外 | Client streaming RPC、双方向 streaming RPC |
| 内容の分割 | 共通手順、前後処理、呼び出し情報、リクエスト情報を独立して扱い、後から章立てを変更可能にする |
| ケースの表現 | 共通手順とケースデータ一覧を分ける。リクエスト JSON やパラメータなどの入力値を一覧から確認できるようにする |
| 期待値 | 対応するステップ・ケースから参照できるようにする |
| シナリオ表の期待結果欄 | ステータスコードを掲載する。受信件数等はセル内に掲載しない。期待値の詳細への参照を組み合わせる案 |
| 実測結果 | レスポンス実測値や実行結果は今回の対象外 |
| 出力 | 既存の Quarto 文書に差し込む、分割された `.qmd` 原稿 |
| 表の記法 | `::: {.landscape}` の内側を `::: {.tbl}` で囲んだ GridTable。生成表は固定で横向きページとする |
| 本文の運用 | 生成した手順はほぼ修正せずに利用する |
| 表様式 | 提示された5列・結合見出しのシナリオ表を基準案とする。列の意味や詳細原稿の様式は引き続き検討する |

以降の具体的な構成・ファイル名・処理方式は、確定事項を満たすための設計案である。本書自身の整理用の表は、生成する手順書の様式を定めるものではない。

- 新ツールは原稿生成を担当し、既存の `_quarto.yml`、章の `index.qmd`、テンプレート機構は更新対象にしない。

- テンプレートリポジトリの `docs/` はサンプルであり、新しい手順書の出力先に固定しない。
- runnora とはファイルで連携する。独立モジュールから runnora の `internal/` を直接 import する構成は採らない案とする。
- 利用者が指定した入力・出力パスを使う案とし、上記3フォルダが常に隣接することを配布後の必須条件にはしない。

## 3. 入出力と原稿の分割案

### 入力

シナリオ YAML を起点に、include 先、ケース JSON、前後処理 SQL を関連付けて読む。runnora の設定、追加 SQL 指定、実行時の作業ディレクトリも、前後処理を再現するための入力情報として扱う。

gRPC の RPC 種別を判別するため、利用可能なローカルの `.proto` と依存ファイル等を参照する案とする。入力の具体的な渡し方は未決定。

### 生成する原稿

次は分割案であり、ファイル名、対象 ID の決め方、ファイル数は表様式に合わせて確定する。該当する情報がない原稿の扱いもその際に決める。

```text
generated/<対象ID>/
├── scenario.qmd       シナリオ概要、共通手順、条件、詳細への参照
├── cases.qmd          ケースデータ一覧、入力と期待値への参照
├── before.qmd         前処理の順序と SQL/PLSQL ファイル名（本文は載せない）
├── after.qmd          後処理の順序と SQL/PLSQL ファイル名（本文は載せない）
├── http.qmd           HTTP メソッド、URL、ヘッダ等
├── grpc.qmd           gRPC 接続先、サービス、メソッド、RPC 種別等
├── request-json.qmd   リクエスト JSON の詳細
├── grpc-request.qmd   gRPC 送信メッセージの詳細
└── expectations.qmd   期待値と検証条件（配置案）
```

- 各原稿は `.landscape` の内側に `.tbl` と GridTable を置き、PDFでは固定で横向きページとする。大きな JSON は詳細原稿に置き、ケースデータ一覧から参照する。
- シナリオ・ケース・ステップの ID と参照ラベルで関連付ける。固定の章番号・ページ番号を識別子として使わない。
- 見出し階層、原稿の配置、並び順は既存文書側で管理する。同じ原稿を、シナリオ別にも情報の種類別にも配置できるようにする。
- 「別ページで起草」は独立した原稿ファイルとして扱う案とする。PDF の改ページは既存文書側で制御し、1原稿を必ず紙1枚に収める制約にはしない。
- ケースごとの入力値は一覧へ分離し、共通手順をケース数分複製しない。条件分岐やケース固有の前後処理は、その適用条件を保持する。

### シナリオ表の基準案

利用者から「現状の形式に最も近い形」として次の例が提示された。以下は受領した例の保存であり、罫線の桁合わせ・ヘッダ境界は組版用に未調整である。

```text
+----------+---------------------------+------------------+------------------+------+
| シナリオ | シナリオ名称                                                           |
+==========+===========================+==================+==================+======+
| 手順番号 | 試験手順                                     | 期待結果         | 結果 |
+          +---------------------------+------------------+------------------+------+
|          | 手順内容                  | リクエストボディ | レスポンスボディ | 良否 |
+----------+---------------------------+------------------+------------------+------+
| 1        | aaaaaを取得する\          |                  | XYZ.json         |      |
|          | GET http:/xxxx/xxxx/aaaaa |                  |                  |      |
+----------+---------------------------+------------------+------------------+------+
| 2        | ccccを登録する\           | ABCDD.json       | QWEE.json        |      |
|          | POST http:/xxxx/xxxx/cccc |                  |                  |      |
+----------+---------------------------+------------------+------------------+------+
```

表は5つの基準列を持ち、先頭行のシナリオ名称は第2～5列を横結合する構成と解釈する。次の見出し行では「試験手順」を第2～3列に横結合し、「手順番号」を2段の見出しに縦結合する。

| 基準列 | 提示例の見出し | 記載内容の設計案 |
|---|---|---|
| 1 | 手順番号 | 共通手順内の順序。元のステップ名との対応も保持する |
| 2 | 試験手順／手順内容 | 操作の説明と HTTP 呼び出し情報表への参照（`URL：表 4.2-1-[1]`）。`URL：` は固定。gRPC は RPC 種別とサービス／メソッドを記載する |
| 3 | 試験手順／リクエストボディ | リクエストの詳細原稿への参照と、参照元JSONが分かる場合は次行にファイル名（パスなし）。複数の場合は改行して列挙する |
| 4 | 期待結果／レスポンスボディ | ステータスコードと期待値の詳細原稿への参照を記載する案。受信件数等や実測レスポンスはセル内に記載しない。下段の見出しは「ステータス・期待値」等への変更を提案する |
| 5 | 結果／良否 | 提示例の空欄を保持する案。生成時には合否を判定・入力しない。利用者が後で記入するかは未確定 |

分割原稿と整合させるため、HTTP のシナリオ表には日本語の手順内容と HTTP 呼び出し情報表への参照を置く。HTTP のメソッド、URL、ヘッダー、クエリは独立した原稿に保持し、シナリオ表と重複させない。JSON の本文と期待条件も独立した原稿に保持する。参照表示は元の JSON ファイル名等を使えるが、実ファイル名のないインラインデータにも対応できる識別子を用意する。

前後処理や DB 操作、bind、条件分岐についてもシナリオ全体の順序・依存関係を失わないようにする。提示例は HTTP 呼び出しのみのため、それ以外を行として出すか関連情報として参照するかは別途定める。

GridTable の結合記法でこの構造を表現できる。手動結合を用いるため `merge-cols` は併用しない案とする。5列分の `widths` を指定し、日本語を含む桁合わせとセル内改行を整える。
提示例の `+===+` はシナリオ名称の直後にあり、このままでは後続の2段の列見出しは表の本文になる。列見出しまでヘッダとして扱い改ページ時に繰り返す案では、`+===+` を見出し全体の末尾へ移す。最終的な見出し繰り返しと改ページは組版時に確認する。

**Q9の回答**: ステータスコードは掲載する。受信件数等は不要。期待結果欄の表示についての回答として、シナリオ表を簡潔にし、元の検証式は詳細原稿で追える構成に整理する。

期待結果セルの具体例（説明用の架空例）:

```text
期待値：[200] 表 4.4-1
XYZ.json
```

この「参照」は実測レスポンスや生の JSON ファイルを開くためのものではなく、既存文書に差し込まれた期待値の詳細表への文書内参照を想定する。表示名には元の期待値ファイル名等を用いる。詳細原稿には期待値の内容・元データの出典・対応する検証式を保持し、別章へ配置しても参照で追えるようにする。

- gRPC では `期待値：[gRPC 0] 表 4.4-1` のように通信方式を併記する。
- ステータスは入力に定義された値・条件から取得する。記載がない場合に HTTP 200 や gRPC 0 を自動的に期待値として補わない。
- ケースごとに異なるステータスは `[ケース別]` とし、対応する詳細表で値を追えるようにする。共通手順のセルで単一値に固定しない。
- ステータス以外の検証式は詳細原稿に保持する案とし、受信件数等をシナリオ表へ展開しない。これは検証そのものの削除や変更を意味しない。
- JSON ファイルを使わない期待条件は、期待条件の詳細表の識別名等で参照する。実在しない JSON ファイル名を作らない。

### 再生成

本文は入力資産を修正して再生成する運用を基本案とする。ツールが管理する生成原稿のみを更新し、既存文書の章構成や手書き本文は上書きしない。

例外的な手編集に備え、前回生成後に変更された原稿を検知・通知する案とする。自動マージは初期版の前提にせず、検知方法と上書き方法は実装設計時に決める。

## 4. 変換処理の構成案

```text
入力収集 → YAML解析 → 参照解決 → 文書用データへの整理
                                   ↓
                        表様式への割り当て → .qmd 出力
```

| 処理 | 役割 |
|---|---|
| 入力収集 | 対象シナリオ、設定、追加 SQL、基準パス、出力先を受け取る |
| YAML解析 | ステップの記述順、識別子、コメント、出典位置を保持して読む |
| 参照解決 | include・JSON・SQL・RPC 定義の関係を解決し、不足ファイルや循環参照を検出する |
| 文書用データへの整理 | 共通手順、ケース、操作、検証式、期待値、条件、出典を保持する |
| 表様式への割り当て | 提示されたシナリオ表を基準に、確定後の列・結合・配置規則を適用する |
| 出力 | 表示幅と Markdown 構文を考慮し、GridTable を含む原稿を生成する |

解析結果と表の列を分離することで、表様式の変更を入力解析へ波及させない。文書用データには元ファイル、ステップ名、行番号、式の原文、静的に確定した値、未解決事項を持たせる案とする。

実装したソース構成:

```text
runnora-docgen/
├── docs/                  設計・運用資料
├── cmd/<コマンド名>/       CLI
├── internal/parse/         入力解析
├── internal/resolve/       参照解決
├── internal/model/         文書用データ
├── internal/render/        様式への割り当てと原稿生成
└── testdata/               入力例と期待出力
```

### 検証式と期待値

- `test` 等の検証式を原文で保持し、対応するステップ・ケース・期待値へ結び付ける。
- 期待値が JSON に定義されていても、実際の検証式で使用されているとは限らない。参照関係を確認できたものと未確認のものを区別する。
- 例えば `current.res.status == vars.case.expect.status` は、原文の式と、静的に分かる場合の期待ステータスを対応付ける。
- 未検証の項目を検証済みの条件として追加しない。完全なレスポンス JSON を推測して生成しない。
- 環境変数や実行時の応答に依存する値は、変数・式・依存関係として残す。文書生成時にシナリオを実行しない方式を推奨する。

### gRPC

Unary と Server streaming は RPC 定義に基づいて区別する。`message` キーだけでは種別を断定できないため、定義が得られない場合は未判定として通知する案とする。文書生成のためにサーバーへ接続しない。

Server streaming は、受信件数と各受信位置に対する検証条件をそのまま保持できる。runnora の既存例には次の条件がある。

- `current.res.status == 0`
- `len(current.res.messages) == 3`
- `current.res.messages[0].sequence == 1`
- `current.res.messages[1].message == "tests passed"`
- `current.res.messages[2].sequence == 3`

添字と「何件目」の対応を示し、記述されていない項目の完全一致や順序条件を補わない。Client streaming・双方向 streaming は未対応として通知する案とし、他の種別に置き換えて解釈しない。

gRPC の送信メッセージは YAML 上の入力表現を保持する。JSON 表示する場合の型・フィールド名等の規則は別途決める。

## 5. 実現性と技術上の注意点

**Go による実現が可能であることを初期実装で確認した。** 既存の入力資産とテンプレートを使い、参照・条件・期待値を中間モデルへ整理して分割原稿を生成できる。表様式の詳細と全 runn 構文への対応は引き続き必要である。

- **YAML解析**: 通常の Go の map の列挙順に頼らず、構文木で記述順と出典を保持する。候補の `yaml.Node` はコメントや行・列位置を持つが、原文の完全再現は保証しない。原文も必要に応じて保持する。[公開仕様](https://pkg.go.dev/gopkg.in/yaml.v3#Node)
- **複数ファイル**: `practice` の suite は template と case JSON を参照するため、単一 YAML の整形だけでは十分でない。データによる繰り返しとリトライを区別する。
- **前後処理**: runnora の前処理順は「共通 before → 追加 before」、後処理順は「追加 after → 共通 after」。SQL パスの基準や include・失敗時の適用範囲は対応仕様を詰める際に照合する。
- **検証内容の忠実性**: 調査した生成 template はステータスのみ検証している。ケース JSON に本文の期待値があっても、本文検証を実施すると記載してはいけない。
- **Server streaming**: runnora の `.proto` とシナリオ、およびローカルの runn v1.9.2 の README に実例を確認した。複数受信の期待条件を文書化できる。[gRPC の RPC 種別](https://grpc.io/docs/what-is-grpc/core-concepts/)
- **GridTable**: セル内の複数段落、箇条書き、コードを表現できる。日本語を含む罫線は表示幅で揃え、バイト数だけで計算しない。[Pandoc Grid tables](https://pandoc.org/MANUAL.html#extension-grid_tables)
- **テンプレート**: `.tbl` は外側の枠、GridTable は内側の表構文。参照は `label="tbl-…"` を使う。罫線の桁合わせと組版後の `widths` は別に扱う。
- **結合・改ページ**: 手動結合と `merge-cols` の併用には制約がある。長い JSON/SQL には表の分割や `breakable-rows` 等を検討し、採用版で確認する。

調査時の runnora は Go 1.26・runn v1.9.2 を指定。テンプレートの `template/VERSION` は 2.0.0、サンプル `docs/.template-version` は 1.4.0 だった。実装時には互換性の基準を固定し、差し込み先文書の機構と版に合わせて検証する。

## 6. 今後決める事項

主要な利用方針は確定した。シナリオ表の基準例を受領済み。以下は、表様式の具体化および実装前に詰める詳細であり、今回は未決のまま明示する。

1. **表様式**: 5列と結合見出し、期待結果欄のステータス掲載を基準に、見出し名、ケース別ステータスの表示、参照表示名、幅、長い JSON/SQL、改ページ、非HTTP手順の表示、各詳細原稿の様式を確定する。
2. **入力の渡し方**: 対象ファイルの指定・順序、設定、追加 SQL、作業ディレクトリ、`.proto` と依存ファイルの指定方法。
3. **対応構文**: include、loop、bind、条件分岐、YAML エイリアス等の対応範囲。シナリオ内 DB runner の詳細やその他 runner の扱い。
4. **説明の入力元**: `desc`・コメントをどう採用するか、説明不足の場合に補足ファイルを使うか。記載されていない業務上の意図は推測で補わない案。
5. **ファイルと参照**: 対象 ID、複数シナリオの出力単位、共通資産の共有、原稿一覧、不要になった生成ファイルの扱い、既存文書内でのラベル衝突回避。
6. **診断・再生成**: 不足参照・未対応機能で停止するか継続するか、手編集検知と上書きの方法。
7. **記録・掲載範囲**: 元資産の版・ハッシュ等の記録、接続情報・認証情報の表示範囲。元シナリオと文書を後から照合できる方式を選ぶ。
8. **配布・互換性**: コマンド名、対象 OS、Go・YAML ライブラリ・文書テンプレートの採用版。

追加の確認が必要になった場合も、1問1答で進める。

## 7. 実装段階の検証計画

- HTTP、Unary、Server streaming、suite/template/JSON、前後処理の代表例で、入力と文書の対応を確認する。
- ステップ順、ケース固有値、条件、検証式、期待値の関係を維持し、実施しない検証を追加しないことを確認する。
- 日本語・特殊文字・長文の原稿を採用版のテンプレートで PDF/HTML にし、表、改ページ、相互参照を確認する。
- 章を並べ替えても参照が成立し、再生成しても既存の章構成や手書き文書を変更しないことを確認する。
- 同じ入力・設定から同じ原稿が生成され、不足参照や未対応 RPC を黙って省略しないことを確認する。

初期実装では単体・結合テストを実行し、runnora の HTTP、Server streaming、suite/template/case JSON、前後処理 SQL の実資産を変換した。生成した全 `.qmd` の Pandoc 解析と、`design-doc-quarto-template` を適用した HTML/PDF 出力に成功した。Petstore サンプルでは全生成表を横向きにして紙面を確認した。

## 8. 実装したコマンド

cobra-cli でアプリケーションと `generate` サブコマンドの雛形を作成し、テスト可能なコマンドファクトリへ整理した。

```text
runnora-docgen
└── generate <runbook.yml>...
    ├── --out, -o
    ├── --config, -c
    ├── --base-dir
    ├── --before-sql
    ├── --after-sql
    ├── --proto
    └── --force, -f
```

`generate` は既存文書の章立てを変更せず、シナリオごとのサブディレクトリへ必要な分割原稿と `manifest.json` を生成する。マニフェストには入力ファイルと SHA-256 を記録する。既存ファイルは既定で上書きせず、`--force` が指定された場合だけ更新する。
